# Задание для Luna: поддерживаемость streaming и terrain

## Цель и границы

Упростить владение состоянием без изменения поведения рендера и движения. Это **не задача устранения GPU-фриза**: полный static solve при смене lighting region остаётся дорогим. Не выдавать рефакторинг за оптимизацию.

По умолчанию выполнить только этап 1, проверить и передать результат. Этап 2 — следующее отдельное задание. Не делать весь план одним большим изменением.

Рабочая директория: `/Users/murasama/Projects/games/Fodislop`.

Обязательные ограничения:

- Соблюдать `AGENTS.md`. Чужие изменения уже есть в большинстве затронутых файлов; не восстанавливать файлы из Git и не переписывать их целиком.
- Unity, Editor/Hub, CLI/MCP, Editor API, импорты, Unity builds/tests и Editor-логи не разрешены.
- Тестовые файлы и проекты тестов не менять: параллельно идёт перенос. Можно запускать существующие standalone .NET-проверки и создавать disposable fixtures вне репозитория.
- Не менять shaders, качество, частоту lighting, точное положение источника, streaming quantum, gameplay delays, протокол пакетов, DI-регистрации и сериализованные ассеты.
- Не добавлять универсальную очередь задач, event bus, новый manager или набор интерфейсов. Сначала использовать приватные методы и существующие типы.
- Обнаруженный самостоятельный баг описать отдельно от механического рефакторинга; не расширять задачу молча.

## Этап 1. Убрать дублирование жизненного цикла streaming-запросов

Основной файл:

`Assets/Scripts/Networking/Connection/Client/Simulation/DummyWorldSimulationState.cs`

Для понимания вызовов читать только:

- `Assets/Scripts/Networking/Connection/Client/Systems/DummyMapStreamer.cs`;
- `Assets/Scripts/Networking/Connection/Client/Responders/DummyMovementResponder.cs`;
- прямо используемые места `Reset`, `OpenAsync`, `Dispose`.

### Что уже работает и должно сохраниться

- `SendMapWindowAsync` — общий путь чтения чанков и сборки одного batch. Не создавать вторую реализацию загрузчика.
- Все нужные дисковые чтения запускаются до ожидания первого; искусственного yield после каждых четырёх payload больше нет.
- Failed/cancelled чтение не публикует частичный batch и не отмечает его чанки отправленными.
- `_sentMapChunks` и `_streamingGate` общие для двух видов запросов.
- Каналы отмены **раздельные**: новое движение заменяет прежний запрос вокруг игрока; новое terrain-окно заменяет прежний terrain-запрос. Нельзя превращать их в одну глобальную latest-wins очередь.
- `_residentWindow` меняется после успешной загрузки окна игрока. Terrain-request не должен перезаписывать его.
- Terrain-request проверяет имя мира, дедуплицирует одинаковый прямоугольник, хранит ссылку на свой слой. После успеха дедупликация сохраняется, после неуспеха допускается повтор.
- Отмена terrain-запроса поглощается его обёрткой; отмена запроса движения доходит до вызывающего кода. Не выравнивать эту разницу случайно.

### Порядок работы

1. Зафиксировать текущую семантику двух путей: кто создаёт/отменяет/dispose-ит CTS, кто захватывает/освобождает semaphore, кто публикует результат.
2. В disposable fixture проверить перечисленные ниже сценарии **до** изменения production-кода. Уже падающие проверки считать исходными дефектами, а не основанием незаметно менять поведение.
3. Выделить минимальную общую механику владения semaphore и cleanup. Допустим приватный helper или небольшой внутренний тип, если он действительно убирает дублирование. Не создавать generic framework с флагами режима.
4. Оставить policy двух запросов в коротких именованных обёртках: замещение, дедупликация, обработка отмены и обновление соответствующего окна.
5. Старое завершение не должно очищать CTS/дедупликацию нового запроса. Сохранять проверку идентичности владельца.
6. Повторить проверки. Показать конкретно, какой дублирующий код удалён. Не добавлять новые слои ради сокращения числа строк одного метода.

### Проверки этапа 1

- Warm batch: нет принудительных ожиданий кадров; cold batch: все чтения начаты до первого ожидания.
- Повтор одного terrain-окна во время запроса и после успеха не запускает вторую загрузку.
- Замена terrain-запроса; замена movement-запроса; два разных канала не отменяют друг друга.
- Отмена до захвата semaphore и после захвата, во время чтения; semaphore освобождается ровно владельцем и не остаётся захваченным.
- Failed read или исключение отправки не фиксирует успех и не теряет возможность последующего запроса.
- `Reset`/`Dispose` во время ожидания; позднее завершение старого запроса не меняет состояние нового.
- Запрос от другого мира игнорируется. Отдельно исследовать `OpenAsync` во время movement-request: сейчас он явно отменяет terrain, но не movement. Возможную правку этого поведения вынести отдельным пунктом, не прятать в extraction.

Для локального старта есть одноразовый fixture `/tmp/kern-streaming-check.KWThzj/`: 26 проверок actual streaming sources и извлечённого residency-check. Он может отсутствовать в другой сессии и не покрывает всю матрицу выше. Не переносить его в тестовые каталоги без нового разрешения.

### Критерий готовности

Одна общая реализация механики semaphore/cleanup, две явные политики запросов, сохранённые результаты/отмена/дедупликация, без новых покадровых аллокаций. Проверки выполнены; остаточные риски названы. Изменения ограничены simulation-кодом и при реальной необходимости маленьким соседним внутренним типом.

## Этап 2. Сделать выбор terrain-окна явным

Отдельное задание после проверки этапа 1.

Читать `LIGHTING_ARCHITECTURE.md`, затем:

- `Assets/Scripts/World/Terrain/Core/TerrainRenderer.cs`;
- `Assets/Scripts/World/Terrain/Core/TerrainViewportCalculator.cs`;
- существующий `StreamingWindow`.

Развести именами и value types три значения:

| Значение | Назначение |
| - | - |
| Requested terrain window | Что требуется загрузить и построить |
| Committed terrain window | Какие cache/mesh/resources уже действуют |
| Camera viewport | Что видно сейчас; не замораживается вместе с ожидающим окном |

Отдельно сохраняется viewport, передаваемый lighting во время ожидания. Это не сам stable lighting region: им по-прежнему владеет lighting coordinator.

Убрать подмену `currentGridPos`, размеров и четырёх viewport-переменных в середине `LateUpdate`. Выделить чистое решение: использовать requested или committed окно. Можно вернуть `readonly record struct` плана кадра, переиспользуя `StreamingWindow`; не вводить иерархию состояний и новые сервисы.

Сохранить порядок: readiness → dirty старого overlap → scroll/build → texture sync → presentation → lighting update. Не объявлять операции атомарными, если ресурсы меняются на месте и rollback отсутствует. Не менять dirty-clear, resize, upload или transport алгоритмы в этом этапе.

Проверки: ожидание начальной загрузки; движение камеры при pending target; resize pending; dirty+scroll по X/Y/диагонали; failed build не публикует новый origin; точный источник продолжает обновляться. Проверять решение и порядок вызовов на actual source в disposable fixture, а не только поиском строк.

## Пока не делать

- Не удалять atlas scroll/reuse вслепую: он связан с kernels, binder, resources, telemetry и проверками. Удаление требует отдельного ограниченного задания с картой ссылок.
- Не объединять terrain и lighting в один размер окна или одну ревизию: у них разные сроки жизни кэшей.
- Не оптимизировать DDA, не включать atlas reuse, не менять invalidation ради прохождения тестов.
- Не распиливать весь `TerrainRenderer` на классы одновременно с исправлением поведения.

## Standalone-проверки и отчёт

Из корня проекта:

```sh
dotnet test tools/Kern.TerrainTests/Kern.TerrainTests.csproj --no-restore --verbosity quiet
dotnet run --project tools/lighting-tests/Kern.LightingTests.csproj -- all
dotnet run --project tools/lighting-tests/Kern.LightingTests.csproj -- streaming
git diff --check
```

`all` сейчас запускает только layout/binding и CPU golden, не transport и не streaming. Эти проверки — страховка соседних компонентов; они не заменяют lifecycle fixture.

Итоговый отчёт: изменённые файлы; удалённое дублирование; сохранённые различия двух каналов; команды и результаты; исходные дефекты отдельно от внесённых изменений. Не утверждать, что исчез фриз или подтверждена визуальная корректность: переход окна в Unity Play Mode в это задание не разрешён.
