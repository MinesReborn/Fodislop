Стандарт пайплайна террейна

Нормативный целевой контракт. Он задаёт владельцев, порядок стадий, форматы передачи данных и критерии завершённого рефакторинга. Текущий код описан отдельно от целевого состояния: существующая структура сама по себе не становится стандартом.

1. Область действия и правила

Стандарт охватывает весь путь от изменения клетки мира до пикселя на экране: координаты и грязные области, планирование окна, захват источников, асинхронную сборку, геометрию клетки, автотайлинг, GPU-упаковку, материалы и атласы, шейдерные проходы террейна, освещение, отладочные слои и выдачу кадра.

Стабильные review IDs: TP-OWN — владельцы и границы модулей; TP-STAGE — порядок стадий и reads/writes; TP-DATA — координаты, единицы и wire format; TP-REV — revision и инвалидация; TP-LIFE — потоки, передача владения и публикация; TP-PERF — стоимость и наблюдаемость; TP-VERIFY — требуемое доказательство; TP-CHANGE — итоговый evidence bundle.

  • У каждой стадии ровно один владелец данных и ровно один владелец жизненного цикла.
  • Стадия получает явный входной снимок и возвращает явный результат. Она не читает скрытое изменяемое состояние предыдущей стадии.
  • Граница главного потока и фонового построения проходит по снимку данных мира. Рабочий поток не обращается к живому хранилищу, сцене, сервисам Unity или глобальному состоянию шейдера.
  • Публикуется только целиком согласованная версия меша, GPU-данных, материалов, дверной накладки и lighting-снимка.
  • Пиксельный рисунок задаётся геометрией и координатой выборки явно. Фильтрация атласа, поля света, постпроцесса и экранного вывода имеют отдельные настройки и не меняют контракт геометрии.
  • Граница Terrain/Lighting подчиняется стандарту Terrain/Lighting. Оркестрация мигрируется только по воротам A–D и в указанном там порядке.

4. Типы данных и единицы (TP-DATA)

  • Мировая клетка: целочисленные координаты Unity мира. Server coordinates не протекают дальше координатной границы; преобразование выполняется один раз через CoordinateUtils и MapManager.WorldHeight.
  • Локальная клетка: нормализованное cell-local пространство. Геометрический grid — целое число делений на клетку; кодирование узла имеет один владелец.
  • Окно/область: полуоткрытый integer rectangle [min, max) с именованным пространством координат. RectInt разрешён только при локальном и явном контракте пространства.
  • Screen pixel, atlas texel и lighting texel никогда не передаются как безымянный Vector2. Для каждой конверсии есть named функция и владелец.
  • Build request — неизменяемый снимок: поколение мира, content revision, origin/size, atlas revision, dirty regions, режим пересборки, worker-safe cell data. Массивы и коллекции не меняются после передачи рабочему потоку.
  • Build result — данные результата и измерения стадий; не содержит ссылки на live Unity objects и не публикуется напрямую.
  • В CPU/GPU wire format указаны диапазон каждого поля, смещение/маска, тип GPU-текстуры, точность, sentinel и правила округления. Encoder и decoder не владеют одинаковой логикой по отдельности: семантика описана один раз, реализации сверяются независимыми ожидаемыми значениями.

Ни один pass не копирует decoder клетки или расчёт геометрии. Общие HLSL функции не получают hidden global state, если значение относится к конкретному frame/material input. Global shader values имеют одного владельца, явный срок жизни и сбрасываются при teardown.

7. Целевая структура модулей (TP-OWN)

Terrain.Contracts
  coordinates, typed regions, geometry/material facts, revision and wire-format schemas
Terrain.Capture
  live storage/metadata access, ring cache, dirty journal, atlas snapshot
Terrain.Build
  frame plan, immutable request/result, topology, fill, tile resolve, mesh encode
Terrain.Presentation
  commit/publish, mesh/material/door views, terrain-owned shader presentation
Terrain.Shaders
  geometry contract, surface contract, pass implementations, shader decoders
Terrain.Diagnostics
  read-only views of stage inputs/outputs, frame-local counters, debug presentation
Lighting.Contracts / Lighting implementation
  remain separated according to the Terrain/Lighting standard
Composition root
  constructs owners once and wires lifecycle; no module locates another via scene search

Структура asmdef — поздний шаг: сначала контракт и зависимости должны быть явными в исходниках. Перенос папок или добавление фасада над старым owner graph не считается модульным разделением.

9. Порядок полного рефакторинга (TP-CHANGE)

  1. Зафиксировать baseline: текущие production inputs, stage timings, field formats, geometry/material snapshots и pixel-space outputs. Unity operation разрешается только прямым запросом пользователя.
  2. Ввести типизированные координаты/region, immutable build request/result и явный capture-vs-worker контракт. Сохранить текущий output и существующий Terrain/Lighting exchange.
  3. Разделить чистые CPU стадии и определить их вход/выход; убрать дубли между полным, scroll и regional путями через общие stage functions, сохранив разные границы обновления.
  4. Зафиксировать geometry/wire schema для C# и HLSL, затем привести все producer/consumer passes к одному contract и independent expected-value coverage.
  5. Разделить build acceptance, GPU/data upload, material binding, door presentation и lighting publication по единому commit transaction.
  6. Уменьшать shader pass graph только после доказательства одинаковой геометрии, alpha, material, emission и AO inputs. Объединение в один pass допустимо лишь если его outputs, lifetime и invalidation остаются раздельно наблюдаемы.
  7. Только после внутренних контрактов переносить файлы, namespace или asmdef; обновить `.meta` и assembly references парно. Orchestration Terrain/Lighting менять только через ворота A–D.

10. Приёмка каждого изменения (TP-VERIFY, TP-PERF, TP-CHANGE)

  • Указаны ID применимых требований, владелец, потребитель, этап и compatibility/wire-format impact.
  • Для request/result указаны mutable ownership, coordinate space/units, thread, generation/revision и точка публикации.
  • Для каждого изменённого stage/pass есть reads/writes, размеры, формат, filter/wrap/mips, clear/load, dispatch/draw bounds, invalidation и stable-frame work.
  • Полный, regional, scroll, texture-refresh, cancellation, world-replacement и held-publication пути используют те же семантические правила.
  • CPU encoder/shader decoder проверяются независимыми известными значениями, включая нули, края диапазона, отрицательные/origin координаты и соседние клетки.
  • Визуальные выводы подтверждаются production path: реальные mesh attributes и SV_POSITION, material keywords, data textures, камера и все активные pass bindings. Изолированный helper не является доказательством.
  • Есть frame-local counters по захвату, worker stages, upload, draw/pass и invalidation reason. Производительность не объявляется улучшенной без сравнимых production captures.
  • Обязательные сканы Terrain/Lighting из TERRAIN_LIGHTING_STANDARD.md проверены; git diff --check чистый; архитектурная документация соответствует фактическому графу.

Если требуемый Unity production check не был прямо запрошен или недоступен, он остаётся явно pending. Этот стандарт не даёт разрешение запускать Unity, импортировать ассеты, собирать Player или менять сцены.
