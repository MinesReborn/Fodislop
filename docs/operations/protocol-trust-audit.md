# Разбор доверия к клиенту

Что клиент сообщает серверу и где он сообщает **результат** вместо
**намерения**. Составлено по определениям пакетов в
`darkar25.kern.networking` и по местам отправки в `Assets/Scripts`.

**Границы разбора.** Проверены исходники клиента и определения пакетов из
`MinesServerNetworking`. Production-реализация сервера в этом checkout
отсутствует. Offline `Dummy` реализует отдельный локальный сценарий и не
подтверждает поведение публичного сервера. Поэтому рекомендации ниже описывают,
что серверу следует проверить; фактическая серверная валидация остаётся
неизвестной.

**Модель угроз.** Считать, что клиент и формат протокола можно изучить и
модифицировать. Сервер может опираться на собственное авторитетное состояние,
которого клиент не контролирует. Обфускация может повысить стоимость анализа,
но не меняет эту границу доверия.

---

## 1. Где клиент сообщает результат вместо намерения

### 1.1. Своя позиция в каждом действии

```csharp
// Assets/Scripts/Networking/Processing/Dispatch/NetworkService.cs
Vector2Int pos = _cachedPlayerController.Position;
Send(new ActionClientPacket((ushort)pos.x, (ushort)pos.y, action));
```

`ActionClientPacket(X, Y, Payload)` несёт координаты, взятые из клиентского
состояния игрока. Это самое крупное место: под ним ходят **все** действия —
копание, постройка, гео, лечение, переключение режимов.

По клиентской реализации видно только, что `X`/`Y` берутся из текущей позиции
локального игрока. Семантика серверной стороны по этому checkout неизвестна.
Если сервер принимает эти координаты как авторитетные без сверки со своей
позицией, клиент потенциально может запросить действие в удалённой клетке.
Если сервер сверяет координаты или использует собственную позицию, этот вывод
не следует из клиентского кода.

**Что проверить на сервере.** Сверять координаты запроса с серверным состоянием
игрока и отклонять действие при несовпадении; отдельно решить, считать ли такие
расхождения диагностическим сигналом. Это рекомендация для проверки, не вывод о
поведении текущего сервера.

### 1.2. Движение задано целью, а не направлением

```csharp
MovePacket(ushort X, ushort Y)   // абсолютные координаты клетки
```

Намерение здесь — «шагнуть вправо», результат — «я в клетке (312, 480)».
Передана вторая форма. Сервер обязан сам проверять смежность с текущей
позицией, проходимость, откат и время с прошлого шага; если он этого не делает,
`MovePacket` — это телепорт по определению.

`RotatePacket(Direction)` передаёт направление, то есть форму намерения. Но по одному клиентскому формату нельзя заключить, как сервер валидирует поворот.

### 1.3. Значения полей ввода приходят от клиента

```csharp
// Assets/Scripts/UI/ServerWindows/Presentation/WindowPresentation/ServerWindowPresenter.cs
_networkService.Send(new ElementClickPacket(windowTag, elementIndex, inputValues));
```

`ElementClickPacket(WindowTag, ElementIndex, Context)` несёт список пар
«имя-значение» из полей окна. Окно при этом **прислал сам сервер**
(`OpenWindowPacket` с полным составом компонентов), то есть серверу известно:

- какие окна открыты у этого игрока прямо сейчас;
- какие в них есть элементы и какие из них вообще кликабельны;
- какие поля ввода есть, какого они типа и какие значения допустимы —
  `SliderPacket` знает свои границы, `IntDropdownPacket` и
  `StringDropdownPacket` — свой список вариантов.

Если сервер сохраняет актуальную схему открытого окна и сверяет клик с ней,
он может отклонять закрытое/неизвестное окно, неверный индекс и значение вне
диапазона или списка вариантов. Наличие схемы в ранее отправленном пакете само
по себе не доказывает, что сервер её хранит или проверяет; это следует сверить
в серверном обработчике. Такие несовпадения — повод проверить запрос, а не
доказательство использования самописного клиента.

Через окна проходят чувствительные операции — магазин, крафт, склад и
улучшения, — поэтому серверная проверка их состояния и допустимых значений
особенно важна.

### 1.4. Приветствие целиком клиентское

```csharp
ClientHelloPacket(int ClientVersion, string OS, int OSVersion,
                  string HardwareFingerprint, string AuthToken)
```

Текущая отправка находится в `ConnectionManager.SendClientHelloIfNeeded`:
`Assets/Scripts/Networking/Connection/Management/ConnectionManager.cs`.

- `ClientVersion` — константа `ClientProtocolVersion.ClientVersion`
  (сейчас `7`). Комментарий клиента описывает серверный version gate; имеющийся
  offline `DummyHelloResponder` тоже сравнивает версии и может отправить
  `OutdatedClientPacket (0)`. Это подтверждает только поведение Dummy и
  ожидание клиента, но не проверку на production-сервере. Version gate в любом
  случае не подтверждает подлинность клиента: модифицированный клиент может
  заявить любое значение.
- `OS` — зашитые строки: `"Windows"`/`"macOS"` по `Application.platform`,
  прочие платформы отдаются как `RuntimePlatform.ToString()`.
- `OSVersion` — только `Environment.OSVersion.Version.Major` (Windows 10/11
  неразличимы).
- `HardwareFingerprint` — `SystemInfo.deviceUniqueIdentifier`.
- `AuthToken` — значение, загружаемое клиентом из `GameTokenStore`
  (`PlayerPrefs` key `AuthToken6`), либо пустая строка при первом входе.
  `AuthTokenProcessor` сохраняет непустой токен из `AuthTokenPacket (45)`;
  кто и на каких условиях выпускает его в production, по исходникам клиента
  установить нельзя.

Ни одно поле не становится доверенным только потому, что его прислал клиент.
`AuthToken` — credential для восстановления сессии; сервер должен проверить его
до привязки соединения к аккаунту, а сам токен считать секретом, а не
доказательством корректности остальных полей. `ClientVersion` может служить
гейтом актуальности клиента, но не подтверждает подлинность клиента. `OS`,
`OSVersion` и `HardwareFingerprint` — заявленные клиентом метаданные; их можно
использовать для диагностики, но они не подтверждают личность и не должны
определять авторизацию, игровые права или серверные лимиты.

### 1.5. Программа робота

`SaveProgramPacket(ProgramId, SaveAndRun, Program, Breakpoints)` передаёт
программу и точки останова. На сервере стоит проверить допустимый размер,
число точек, операции и частоту запросов. Серверный код в этом checkout не
проверен, поэтому наличие или отсутствие таких ограничений неизвестно.

## 2. Инварианты, которые сервер может проверять уже сейчас

Данные для них в протоколе есть, дополнительных полей не требуется.

**Метка времени конверта.** `ClientPacket(uint Timestamp, IRootClientPacket)`.
В клиентском коде в неё записываются `(uint)DateTimeOffset.UtcNow.Ticks`. Это
младшие 32 бита UTC ticks: значение циклически переполняется примерно каждые
429,5 секунды, поэтому его нельзя использовать как абсолютное время для окна
сверки с серверными часами. Часы системы также не гарантируют монотонность.
Если серверу нужны порядок или обнаружение повторов в пределах соединения,
нужен отдельный счётчик последовательности и серверная проверка состояния
счётчика. Такой счётчик сам по себе не аутентифицирует клиента и не защищает от
подделки; добавление требует согласованных изменений обеих сторон протокола.

**Порядок.** Сервер должен проверять состояние и допустимые переходы на момент
обработки: например, доступно ли окно для клика и готов ли мир к игровому
действию. Из-за задержки или повторной отправки приложение может обработать запрос после
изменения состояния; гарантии конкретного транспорта этим клиентским аудитом
не установлены. Поэтому порядок, необычный для наблюдаемого UI, сам по себе не
доказывает нарушение.

**Бюджеты на тип действия.** Лимиты частоты могут ограничивать нагрузку и
повторные операции, но должны учитывать cooldown, RTT, повторную отправку и
штатный игровой поток. Превышение одного лимита — сигнал для проверки запроса,
не самостоятельное доказательство бота или основание для санкции.

## 3. Проверочные сценарии для серверной валидации

Случаи ниже полезны как отрицательные тесты обработчиков, а не как скрытые
production-ловушки. Они проверяют границы доверия, не меняя видимое игроку
содержимое мира.

- Клик по закрытому/неизвестному окну или индексу, которого нет в сохранённой
  серверной схеме.
- Значение поля вне объявленного сервером диапазона или списка вариантов.
- Действие для клетки, предмета или состояния, недоступных игроку по текущему
  серверному состоянию.
- Неизвестное или некорректное поле пакета, включая несовместимую версию
  сериализации.

Ожидаемый результат для каждого сценария — отказ без побочного изменения
игрового состояния. Диагностику лучше агрегировать или ограничивать по частоте,
чтобы некорректные запросы не создавали log flood. Один отказ не должен
автоматически приводить к отключению или санкции: сначала нужно исключить
устаревшее состояние окна, повторную отправку, сетевую задержку и несовпадение
версии протокола. Любое дополнительное telemetry-поле требует оценки
приватности, срока хранения и реальной пользы.

## 4. Телеметрия и ограничения статистики

Распределения действий могут помочь заметить повторяющиеся аномалии, но этот
checkout не содержит данных, подтверждающих универсальные «человеческие»
пороги. RTT, потери и повторы пакетов, частота кадров, устройство ввода,
доступность и особенности сценария влияют на интервалы и траектории.

Для исследовательской телеметрии можно сравнивать последовательности действий
с серверными правилами: повторные запросы, частоту действий относительно
cooldown, недопустимые координаты и долю отказов. Сначала нужно определить
базовые распределения на репрезентативных сессиях и отдельно учитывать RTT и
версию клиента. Статистический сигнал должен вести к проверке, а не заменять
серверную валидацию или сам по себе запускать санкции.

---

## 5. Чего не делать

Обфускация и проверки только внутри клиента не должны быть границей
безопасности: модифицированный клиент контролирует локальные данные и может
обойти такие проверки. Они могут повысить стоимость анализа, но не заменяют
серверную проверку. Аппаратный fingerprint также является сообщаемой клиентом
метаинформацией, а не подтверждением личности. Необходимость отдельного
anti-cheat-решения следует оценивать по модели угроз и стоимости поддержки;
этот аудит её не устанавливает.

---

## 6. Порядок работ

1. Проверить серверную сверку `ActionClientPacket.X/Y` с позицией игрока.
2. Проверить серверное состояние окон и валидацию `ElementClickPacket`.
3. Проверить смежность, cooldown и текущую позицию при обработке `MovePacket`.
4. Настроить rate limits из cooldown и легитимного игрового потока; измерить
   ложные отказы при высоком RTT и повторной доставке.
5. Только если есть требование к порядку/дедупликации, определить отдельный
   connection-scoped sequence в обеих сторонах протокола. `Timestamp` для этого
   не подходит.
6. Добавлять телеметрию только после определения цели, срока хранения и
   того, что она не ведёт к автоматическим санкциям по одному сигналу.

Пункты 1–4 используют существующие клиентские поля, но требуют проверки и
изменений серверной стороны; этот checkout не показывает, реализованы ли они.
Пункт 5 — изменение протокола с совместной реализацией клиента и сервера.
