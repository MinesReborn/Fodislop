# Критерии готовности игры

Этот документ — Definition of Alpha Ready для клиента Fodinae. Каждый критерий: **ID** · формулировка «если игрок делает X → система делает Y за N секунд / с численными пределами» · **где проверяется** (сборка / автотест / ручной сценарий против публичного сервера). Документ — единственный источник перечня готовности; автоматизируемые пункты мапятся на существующие гейты (см. §13).

---

## Рамка: о чём игра

Научно-фантастический сэндбокс в далёком будущем. Игрок — оператор робота-шахтёра на работе у космической федерации; сотни и тысячи роботов спускаются в недра планет добывать кристаллы для федерации.

Первые 30 минут — обучающая база: локация мира с заданиями, где новичок осваивает основные механики и немного знакомится с лором; после прохождения игрока выпускают в открытый мир.

Основной цикл: копка → добыча кристаллов → сдача федерации за валюту → покупка/улучшение роботов и снаряжения, здания, кланы, ежедневные миссии.

## Определение «готово»

**Клиент готов, если:** любой человек скачивает билд (Windows + macOS), запускает, проходит обучение без блокировок, играет непрерывно ≥2 часов без краша; разрыв соединения = возврат в меню без потери данных (кроме кристаллов при смерти); 60 FPS на среднем и ≥30 FPS на слабом железе; при RTT ≤150 мс движение и копка играбельны без «телепортов»; все системы из перечня этого документа подтверждены чек-листом против публичного сервера.

- Альфа **открытая** (все желающие).
- Платформы альфы: **Windows x64 + macOS ARM64**.
- Подключение: **один публичный сервер, адрес зашит в билд**.
- В игре один зарегистрированный серверный адрес по умолчанию (дефолты `ServerHost`/`ServerPort` в билде указывают на продакшн).

## 1. Вход и онбординг

- **EDGE-01** Запуск установленного билда (Windows/macOS) → главное меню отзывается за ≤10 с от оформленного запуска.
- **EDGE-02** В главном меню есть кнопка входа на вшитый публичный сервер (адрес зашит в билд). Работает по умолчанию без ручного ввода IP. Лента серверов и ручной ввод IP не обязательны.
- **EDGE-03** Первый вход: клиент шлёт `ClientHello` → сервер создаёт аккаунт (`GenerateUniqueNick`), возвращает `AuthTokenPacket`; повторный вход по сохранённому токену (PlayerPrefs `AuthToken6`) авторизует тот же аккаунт. Игрок не видит ни одного экрана регистрации.
- **EDGE-04** Обучающая база — локация мира с заданиями (строится с нуля). Новый игрок доходит от входа до «выпуск в открытый мир» за ≤30 минут; ни один шаг обучения не блокируется (нет «застрял — задание не выдалось», «застрял — маркер не виден»).
- **EDGE-05** Русские тексты финальные (обучение, лор, программатор, настройки, подписи эффектов, меню). en/zh/zh-hant функциональны: переключение языка без краша и без отсутствующих ключей.
- **EDGE-06** Выход на сервер / «играть» / «discord/патч» — действия из главного меню не роняют клиент и не оставляют виснущих экранов.

## 2. Персонаж: движение, копка, стройка

- **MOVE-01** Движение — строго команда-подтверждение: шаг → `MovePacket` → позиция устанавливается по подтверждению сервера. При RTT ≤150 мс нет «телепортов» и рывков позиции; команды не накапливаются бесконечно при задержках.
- **MOVE-02** Кулдown копки 0.3 с; повторные шаги и копка не отправляются до подтверждения текущего действия. Направление по умолчанию — Down (`_lastSentDirection`).
- **MOVE-03** Копка клетки: клиент шлёт `ActionClientPacket(x, y, new BzPacket())` → сервер поворачивает робота к клетке и применяет урон прочности (`World.DamageCell`; зависит от скилла Digging и типа клетки). Клетка не разрушилась — пакет перезаписи не отправляется, клиент видит только эффект удара (`VFXPacket`/`DirectedFX.Bz`), прочность хранится на сервере. Клетка разрушилась — сервер пишет тип 0 (пусто) и рассылает единственным пакетом перезаписи `MapRegionPacket(x, y, 0, 0, [тип 0])` (вырожденный 1×1 регион; тот же пакет, что стримит чанки) → `MapRegionProcessor` перезаписывает клетку; результат виден ≤1 с при RTT 150 мс.
- **MOVE-04** Стройка/заполнение клеток сервер-авторитетна; результат виден ≤1 с при RTT 150 мс; проходимость валидируется сервером.
- **MOVE-05** Блокировка ввода (инвариант `InputBlockState`): фокус чата, открытое окно, пауза полностью блокируют движение и копку. Стрелки/WASD/Enter/Tab не перемещают фокус по кнопкам UI.
- **MOVE-06** Координаты единые: серверные Top-Left, преобразования только через `CoordinateUtils`; ни в одном сценарии игрок не «проваливается» по Y.

## 3. Смерть и возрождение (без PvP)

Агрессия (клавиша L, атака игрока на игрока, урон между игроками) **вырезается полностью** из клиента и сервера и в объём альфы не входит.

- **DEATH-00** В клиенте нет элементов агрессии: ничего не шлётся, никаких подписей/HUD/обработчиков атаки игрок-на-игрок.
- **DEATH-01** Смерть робота (источник урона — опасности мира; список источников см. открытый вопрос в конце документа): теряются **только кристаллы**, инвентарь сохраняется; возрождение у своей точки `Resp` (здание Resp); клиент показывает факт смерти и возврат без потери остального состояния.
- **DEATH-02** Если в пределах охоты робот по всем источникам урона неубиваем — `DEATH-01` сокращается до требования сохранности состояния при любых аварийных ситуациях (§10).

## 4. Инвентарь, статы, крафт

- **INV-01** Сетка инвентаря 9×6 + хотбар: предмет кладётся/берётся/выбирается/используется; состояние согласовано с сервером; изменение видно ≤1 с.
- **INV-02** Статы: HP/энергия/баффы приходят с сервера (`StatusProcessor`, `PlayerInfoProcessor`) и обновляют HUD; изменение видно ≤1 с.
- **INV-03** Крафт `Crafter`: рецепты из `recipies.json` отображаются; создание предмета исполняется сервером; расход ресурсов и результат видимы.
- **INV-04** Хранилище `Storage`: положить/взять ресурсы; объём и содержимое синхронизированы с сервером, переживают перезапуск клиента.
- **INV-05** Предмет нельзя «потерять» по вине клиента: подтверждения операций проходят через сервер (никаких локальных «убрал, а не сохранилось»).

## 5. Мир, стриминг, карты

Общий размер мира — **30 000 × 60 000 клеток**, чанки 32×32. Игрок видит только область на экране — примерно **5×3 чанков (~160×96 клеток)** вокруг робота.

- **WORLD-01** `WorldInitPacket` → `MapStorage.IsReady` → рендер террейна. До готовности мира экран загрузки показывает состояние, элементы игры не мелькают по отдельности.
- **WORLD-02** Стриминг чанков 32×32 по миру 30к×60к: рендер и загрузка только области ~5×3 чанков вокруг робота; за краем viewport — кэширование в RAM/диск (`*.mapb`); движение и заход в глубину без просадок кадра, без перестроения геометрии за пределами viewport.
- **WORLD-03** Конфиги клеток: текстуры, анимации (семантика `FrameOffset=0` валидна), разрушение и восстановление клеток согласованы с сервером; FX разрушения/добычи эмитятся (`SendFx` — см. §12, в правках).
- **WORLD-04** Карты:
  - **Миникарта** — только окрестность робота: живое состояние клеток рядом с ним.
  - **Полноэкранная карта мира** — весь мир, уже открытый игроком: состояние чанка, зафиксированное **в момент последнего посещения** (снапшот, не real-time); повторный заход в чанк обновляет его снимок на карте; позиция игрока на карте — живая отметка.
  - Клики по картам через `RuntimePanelUtils.ScreenToPanel` — без ложных `ClickCellPacket` (движение/копка не возникают от клика по UI).
- **WORLD-05** Камера следует за роботом; зум/плавное движение не перестраивают геометрию каждый кадр (инварианты coverage/zoom-кэшей); ограничения z-порядка камер меню/игры не ломаются при переходах.
- **WORLD-06** Освещение: lighting field кратным целым числом тексел на клетку, регион смещается шагом 8 клеток; смена качества не ломает фазу освещения.
- **WORLD-07** Координаты сохраняются: позиция игрока после перезапуска клиента/сессии восстанавливается сервером (или корректно сообщается о невозможности).

## 6. Роботы и программатор

Клиент-редактор + сервер-VM. Сегодня клиентский редактор локальный (список программ `Codes`/`Labels`/`Values`, `programmator.json`), а на сервере есть VM (`RunningProgramState`) и сериализатор (`ProgramSerializer` V1/V2/V3). Мост «редактор ↔ VM» отсутствует — он реализуется в альфу.

- **ROB-01** Клиент-редактор (сетка программ, ячейки = коды операторов + метки/значения) создаёт/редактирует программу и **отправляет её на сервер**; сервер-VM исполняет на роботе.
- **ROB-02** Реализуется **полный реальный протокол программатора клиент↔сервер** на весь жизненный цикл (не «заглушки»):
  - список программ (клиент получает/отправляет перечень);
  - открытие / создание / переименование / удаление программы;
  - сохранение: клиентские `codes`/`labels`/`values` сериализуются в формат VM через `ProgramSerializer` V1/V2/V3 и обратно;
  - запуск / пауза / остановка;
  - пошаговое исполнение (`StepIn` / `StepOut` / `StepOver`);
  - точки останова (`BreakpointHit`);
  - запрос памяти и состояния (`QueryProgramMemory` → `ProgramMemory`);
  - прогон VM на роботе и рассылка состояния (`ProgramState` / `UpdateProgram` / `OpenProgrammator`);
  - обновление UI редактора по ходу выполнения.
  Базис протокола — серверные `RunningProgramState`, `ProgramSerializer`, `ProgAction` и клиентские `ProgrammatorOperators`. Состав пакетов определяется реальным потоком «редактор → VM → робот → редактор»; каждая пара пакетов обоснована этим потоком (без мёртвых и без чисто визуальных).
- **ROB-03** Диагностика: невалидная программа (неизвестная инструкция, некорректная сериализация) → понятное сообщение в редакторе, без падения клиента. Run/Stop реально управляют роботом через сервер (не только состояние кнопок).
- **ROB-04** Локальное сохранение списка программ (`programmator.json`) продолжает работать; после перезапуска клиента список восстанавливается в редактор; сервер остаётся источником факта выполнения.
- **ROB-05** Спавн и позиции роботов (`BotId`, чужой/локальный) рассылаются корректно во время выполнения программ; локальный игрок на своём роботе плавен.

## 7. Миссии и клановые задания

- **MIS-01** Федерация выдаёт ежедневные миссии; **сброс в 18:00 МСК**; выдача/выполнение/награда (валюта, кристаллы) реально работают через `Mission*`-пакеты (сегодня сервер их не шлёт — см. §12, в правках).
- **MIS-02** Стрелка миссии видима и ведёт к цели (фикс `MissionArrowUI` — сейчас элемент невидим) в любом из заданий обучения и ежедневок.
- **MIS-03** Клановые задания: выдаются, засчитываются, прогресс прокачки клана отображается и влияет на клан (роли, права).

## 8. Экономика и окна

- **ECO-01** Кристаллы → серверная конверсия в валюту → покупки. Замкнутый контур «накопал → сдал → купил» работает без ручных правок данных.
- **ECO-02** Серверные окна (`OpenWindowPacket`) открываются со структурой и данными и корректно закрываются: **Storage** (хранилище), **Bshop** (магазин ботов), **Up** (апгрейд-станция), **Crafter** (крафт), **Market** (магазин/NPC), **Донат-магазин** (магазин предметов на **игровую валюту**; реальных платежей в альфе нет), **Аукцион** (выставить/купить предметы между игроками).
- **ECO-03** Закрытие окон — **только** по `CloseWindowPacket` (сервер авторитетен); ESC/кнопка закрытия шлют запрос серверу; локально окно не скрывается.
- **ECO-04** Здания в объёме альфы: **Storage, Market, Resp, Crafter, Up, Gate + Teleport, Gun, Bshop, Mayak**. Каждое строится/используется с согласованием сервера; Gate/Teleport реально перемещают робота.
- **ECO-05** Донат не связан с реальными деньгами на этом этапе; любой «платёжный» флоу в клиенте либо убран, либо работает тестовой валютой, без платежного API.

## 9. Чат и аудио

- **CHAT-01** Global/local/floating чат работают с сервером: отправка, приём, история канала; фокус ввода чата блокирует геймплейные клавиши.
- **CHAT-02** Чат не съедает события: сообщения не теряются при активном взаимодействии (тяжёлая копка/движение). Enter отправляет сообщение при открытом поле чата.
- **AUD-01** Банки FMOD в билде альфы обязательны: **UI и меню**, **SFX копки/добычи/разрушения**, **музыка мира/зоны**. Отсутствие банка фиксируется как `Degraded`, но не блокирует вход.
- **AUD-02** Шины Master/SFX/Music/UI/Ambience/3D: громкости сохраняются между сессиями и применяются к нужным звукам.
- **AUD-03** 3D-SFX позиционируются у источника (копка, взрыв рядом слышны именно рядом); обновление звука не рвётся при движении.

## 10. Настройки и стабильность

- **SET-01** Все настройки валидируются (`SettingsProbe`), применяются на старте, сохраняются атомарно: `client_config.json` schema v15 с миграциями и backup. Набор: разрешения, HDR, громкость, язык, качество.
- **SET-02** Переключение настроек применяется без перезапуска игры; язык переключает UI и тексты на лету (`OnLanguageChanged`).
- **REC-01** Разрыв соединения или перезапуск сервера → **возврат в меню** с понятной диагностической ошибкой; без краша, без зависшего экрана/оверлея, без «зомби»-подписок.
- **REC-02** Сессия ≥2 часов без деградации (память/ФПС/стриминг/аудио не растут и не рвутся); 50 циклов «меню ↔ игра» не оставляют объектов, подписок и задач; 24-часовой мониторинг метрик (nightly soak) не фиксирует утечек.
- **REC-03** Аварийное состояние во время записи чанка не теряет dirty chunk: атомарный save с backup; `client_config.json`, карта мира (`*.mapb`) и `programmator.json` восстанавливаются корректно.
- **REC-04** Никаких искусственных FPS-caps, frame skipping и троттлинга (запрещено инвариантами проекта).

## 11. Производительность

- **PERF-01** 60 FPS на среднем железе (дискретная видеокарта, ~1080p) и **≥30 FPS на слабом железе** (офисный ноутбук со встроенной GPU, ~1366×768) — при движении, копке, заходе в глубину, стриминге новых чанков.
- **PERF-02** При RTT ≤150 мс движение и копка играбельны: без «телепортов», без накопления команд, без подтормаживаний, списанных на сеть.
- **PERF-03** Стриминг мира 30к×60к не вызывает просадок кадра; рендер области ~5×3 чанков стабилен по времени кадра (бисекция через F4/F6/F7/F8, бюджет по `FrameProfiler`).
- **PERF-04** GC alloc/frame в зафиксированном бюджете (baseline фиксируется калибровочной сессией); память в долгой сессии (≥2 ч) остаётся плоской.
- **PERF-05** Lighting field целым scale; SRP Batcher включён; нет per-frame перестроения геометрии на плавном движении/зуме.
- **PERF-06** Отчёты замеров не ссылаются на VSync/частоту монитора/Editor overhead как на причину (см. инварианты проекта). Всё, что измеряем, объясняется работой кода.

## 12. Протокольные правки сервера (подготовка к альфе)

Все пункты согласованы как обязательные для альфы (клиент+сервер):

- [ ] **Программатор — полный реальный протокол** (см. ROB-02): связный набор пакетов всего цикла «редактор → VM → робот → редактор», каждая пара обоснована потоком; формат — через существующие `RunningProgramState`/`ProgramSerializer` (V1/V2/V3)/`ProgAction`.
- [ ] **Миссии**: сервер реально шлёт `Mission*`-пакеты (выдача ежедневок, сброс 18:00 МСК, награды) — сейчас не шлёт; клиентские процессоры подключаются к флоу (см. MIS-01).
- [ ] **`ClientVersion` валидируется сервером**; устаревший клиент получает `OutdatedClientPacket` и понятный экран с текстом об обновлении.
- [ ] **`ChatListPacket` / `MaxDepthPacket` / `SelectItemPacket`**: разобрать соответствие клиента и сервера — реализовать или убрать согласованно с обеих сторон, чтобы не было «клиент ждёт, сервер не шлёт».
- [ ] **FX-эмиссии** (`SendFx`/`SendDirectedFx` сейчас пусты): вернуть для копки, разрушения, добычи кристаллов (см. WORLD-03).
- [ ] **Выход из объёма:** агрессия (PvP) убирается из сервера и клиента (см. DEATH-00).

## 13. Автоматические гейты поверх критериев

Автоматически проверяемое мапится на существующие гейты проекта (нового кода почти не требуется):

| Критерии | Гейт |
|---|---|
| EDGE (вход), MOVE, INV, WORLD, ROB, MIS, ECO, CHAT, AUD — инварианты кода | ArchitectureLinter «все правила» (47 ID), `dotnet run --project tools/Fodinae.ArchitectureLinter` |
| Конфигурация/миграции (SET-01) | Правило `FOD-SETTINGS-PROBE` линтера (defaults/ranges/consumers/localization) |
| UI-инварианты: is-hidden, ScreenToPanel, одна тема USS, локализация | Правила линтера `FOD-UI-*`, `FOD-LOCALIZATION`, `FOD-HARDCODED-TEXT`; `Fodinae.DisplayTests` |
| Сцены/переходы (REC, EDGE) | `dotnet test Fodinae.TerrainTests`, EditMode/PlayMode-тесты (SceneTransition) |

## Открытые вопросы (фиксировать до старта замеров)

- **Источники урона/смерть в альфе.** После вырезания агрессии и при «мобы вне альфы» остаётся ли то, что может убить робота: опасности мира (бомбы/взрывы кристаллов при добыче, падающие клетки, зоны урона)? Если смерть невозможна — `DEATH-01` заменяется только требованием сохранности состояния (см. DEATH-02).
- **Фиксация performance baseline** (PERF-04/PERF-06): одна калибровочная сессия на референс-железе (слабый и средний), после которой бюджеты p95/GC/память считаются нормой; регрессия >5% — нарушение.
